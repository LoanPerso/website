  Analyse

  Ce qu'est /admin/mail/simulate : l'« autre côté » du smoke webmail. Comme la
  messagerie est une maquette adossée à la base (aucun IMAP/SMTP), simulate.ts
  injecte des messages direction:'in' dans la boîte Quickfund. Le bac à sable
  permet de répondre en tant que l'interlocuteur dans un fil existant
  (simulateReplyTo) ou de créer un mail entrant de zéro
  (simulateInboundMessage). Le round-trip (envoi depuis le webmail → apparaît
  côté simulate → réponse) fonctionne déjà via thread_key.

  Le problème : la page actuelle (307 lignes monolithiques) est « moche » —
  liste étroite + volet droit avec formulaire max-w-2xl centré et bulles
  ml-8/mr-8 n'affichant que des snippet tronqués. Elle ne reflète pas le langage
  visuel soigné du vrai webmail (MessageList, MessageView, ComposePane).

  Le plan — refonte en miroir fidèle du webmail, en réutilisant les tokens et
  composants partagés (grayscale/Linear, conforme à la charte) :

  1. Données : ajouter listMessagesFullByIds (corps complets du fil ouvert — le
  webmail lit les corps entiers, pas des snippets).
  2. Composants (app/_components/admin/mail/simulate/, découpage par feature) :
    - types.ts — modèle SimulateConversation + buildConversations
    - conversation-list.tsx — volet liste (style MessageList : recherche,
  expéditeur/objet/aperçu, sens du dernier message)
    - conversation-thread.tsx — lecteur en cartes empilées (corps complets,
  en-tête type MessageView) + composer de réponse ancré
    - new-mail-form.tsx — composer inline « nouveau mail entrant » (style
  ComposePane : presets, compte cible, expéditeur, objet, message)
  3. Page : orchestrateur 2 panneaux responsive (mono-panneau mobile avec barre
  retour, comme le webmail).
  4. Docs : JOURNAL, CHARTE_GRAPHIQUE, FEATURES, PROJECT_STATUS.

  Conforme aux règles : zéro modal (panneaux inline), grayscale, composants
  partagés. Je commence.
